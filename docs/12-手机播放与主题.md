# 手机播放、音乐绑定、多架构与屏幕主题

2026-11-03：Python 3.11.18/3.12.3 各 77 项本机离线测试通过，工作流 YAML/Compose/静态/脚本检查通过。Chromium 验证了主题、二维码、登录驱动入口撤销、权限过滤和无脚本横屏页；未调用真实登录/搜索/播放，也未执行或发布 ARM64 镜像。ARM64 已由用户提供，原生构建/容器测试、实际 R76s/Kindle/账号验收仍待执行。

## 原生 DLNA 与蓝牙

第三代大脑没有替换音箱固件的蓝牙 A2DP Sink，也没有让 R76s 接管蓝牙/声卡。原来能用的手机蓝牙播放路径原则上保留；自动语音中断现在只有在平台持有活动任务时才发送 stop，没有平台任务时不停止手机原生音乐。

不能从源码保证 DLNA 当前在线：历史记录中出现过 KPlayer/发现服务无响应，见 [音频链路](05-音频链路真相.md)。新服务采用 601 播放，不自动启动或替换 DLNA。因此蓝牙、原生 DLNA 和本平台 UI 点歌需要分别验收。

扬声器和播放器共享。用户主动点歌、TTS、闹钟会抢占声音；夜间规则也会影响手机播放。目前没有蓝牙/DLNA 曲目信息和播放所有权的完整回传，不能保证切入后自动续播或显示准确曲名，不要为测试随意改 DSP/MCU/音量。

## AirPlay 可行性

AirPlay 并不等于屏幕镜像/视频，它也有独立的[音频投送](https://support.apple.com/en-us/105068)。苹果控制中心或音乐 App 选择 AirPlay 扬声器使用 AirPlay 音频协议，不是 DLNA。Shairport Sync 方案只接收音频，不接收镜像或视频。安卓没有统一的“隔空音频”协议：根据 App/设备，可能是 [Google Cast](https://developers.google.com/cast/docs/overview)、DLNA 或蓝牙；不能仅凭“投屏/投送”按钮判断协议。

可行路线是 iPhone/iPad → [Shairport Sync](https://github.com/mikebrady/shairport-sync) → R76s PCM 管道 → 有界实时 MP3 → control 唯一调度器 → 音箱 HTTP/601。使用成熟接收器，不手写协议、不接管音箱声卡。

官方支持 pipe/STDOUT，但后续 HTTP/固件播放不在其同步控制内。Classic AirPlay 源端约 2 秒延迟，后续转码/缓冲还会增加延迟；不承诺视频口型、游戏或 AirPlay 2 多房间同步。

**本轮只是可行性评估，没有启用 AirPlay 接收器、服务广播或新端口。** 真正实现还需要固定接收器版本、LAN mDNS/TCP/UDP 策略与认证、固定 PCM 格式、有界直播环形缓冲、会话 generation/取消/来源元数据，以及真机首尾/重连/长时/延迟验收。AirPlay 2 与 NQPTP 单独设范围。源码里的 AirPlay 注释不是固件已支持它的证据。

## 网易云 Web UI 扫码

不需要安装 [NetEase/skills](https://github.com/NetEase/skills) 才能语音播放。它是 Agent 操作指南，不代替官方 CLI、开放平台 App ID/Private Key、账号授权或本应用工具权限。

音乐 → 应用凭据 → 更新 App ID/Private Key → 扫码登录。PEM 私钥通过 `--` 参数终止符传入，避免被当成 CLI 选项；播放器设为本项目的模拟 mpv URL 捕获器，不在 R76s 本地出声。

使用已核对的官方 `login --background`，从官方链接生成 PNG 二维码。进程退出 0 不等于已绑定：页面每 4 秒调用 `login --check`，分别显示待配置、未绑定、等待扫码、已绑定、过期、失败和未知；成功/过期后移除二维码，不回显原始 CLI 日志、Cookie 或 token。过期后再按“扫码登录”生成新链接。

账号卷持久化 CLI 登录态，重启后必须重新检查，不能盲目恢复“已绑定”。真实账号未验收；本轮二维码与授权变化的浏览器检查是明确的离线夹具。

## 推荐、红心与收藏

音乐页新增每日推荐、红心、收藏歌单、播放列表和加入队列；语音增加 `play_music_collection`，共用受限 resolver 和调度器。收藏歌单先打开具体歌单，再播放列表。

个人入口按登录和目录权限变化：未绑定/扫码中/过期/状态未确认时禁用；绑定成功后自动检测目录，只有实际支持的项启用。退出、凭据更新或状态失效会撤销入口并移除当前个人列表，迟到的目录结果不能恢复权限。缓存/本地入口不受影响。后端也重新检查授权，不能只靠 UI 禁用。

业务命令是动态目录。适配读取实际 `commands`，兼容父/子缩进结构，只匹配以下固定白名单；缺失时显示“当前账号未提供”，不伪装成空列表：

| UI | 仅在实际目录匹配时调用 |
| --- | --- |
| 每日推荐 | `recommend songs` / `recommend daily` |
| 红心 | `playlist liked` / `playlist likelist` |
| 收藏歌单 | `playlist collected` |

目录匹配、参数和集合返回格式使用离线夹具验证；安装版 0.1.7 未登录静态目录没有这些动态项。真实账号权限、额度、目录和返回格式仍需验证。集合调用携带 `--userInput`，不绕过会员/版权限制；`visible=false`/`playFlag=false` 项不能入队。

列表一次最多 50 首，用户停止/切换 generation 后旧列表不能迟到恢复播放。媒体 GET、设备接收和实际听到声音仍分别记录。

## ARM64 与 AMD64

R76s 架构已由用户确认是 ARM64。本机没有 Docker daemon：新增双架构构建/发布入口，但未生成或上传实际镜像。

[docker-bake.json](../docker-bake.json) 只构建 Compose 使用的统一 `runtime` 目标，包含 `linux/arm64` 和 `linux/amd64`；[构建工作流](../.github/workflows/images.yml) 手动构建，显式 publish 后以 `:latest` 推送 GHCR manifest list。日常发布到 Docker Hub 使用根目录 `start.sh push`。基础镜像仍固定摘要。

```sh
docker buildx create --name spk-multi --driver docker-container --use
IMAGE=ghcr.io/your-owner/neteast-spk-server:latest \
  docker buildx bake -f docker-bake.json --push
docker buildx imagetools inspect ghcr.io/your-owner/neteast-spk-server:latest
```

跨构建需要 QEMU 或双原生节点，工作流配置 QEMU。传统 image store 通常不能 `--load` 双架构 manifest；离线包使用 OCI exporter。设置 `SPK_IMAGE` 后 `docker compose pull`、`docker compose up -d --no-build`，R76s 选择 ARM64，x64 主机选择 AMD64。registry token 仅在可信终端/工作流使用。

x64 不是绝对不能执行 ARM64，而是需要 QEMU/binfmt；没有仿真或原生 ARM 节点时，ARM64 阶段的 `RUN` 会出现 `exec format error`。本轮核对并修改了以下构建/测试路径：

- 前端字体/图标资产在 `BUILDPLATFORM` 生成；resolver 的 Node 二进制和依赖仍从目标架构 `node-runtime` 阶段复制，不能把 x64 Node 塞入 ARM64 镜像。
- Python `pip install` 使用 `--only-binary=:all:` 和锁定 hash，缺 wheel 时明确失败，不在 QEMU 中偷偷进行未准备的源码编译。已核对主要原生依赖的 Python 3.11 ARM64 wheel 元数据，但这不代表动态库或镜像实际运行通过。
- 发布前置 `native-smoke`：AMD64/ARM64 使用对应原生 runner，先核对 `uname -m`，构建单架构 runtime 镜像后执行预检和回归。runtime 本身包含 Node，回归直接在将要发布的同一镜像中运行。
- 回归只读挂载在 `/app/tests` 等仓库对应路径，测试镜像自己的 `/app/src`，不以宿主源码覆盖镜像代码。ARM runner 不可用时需配置受控原生节点，不能假装在 x64 上通过 ARM 运行测试。
- 已修复工作流 `[[ ... ]]` 被 YAML 误解析、测试文件路径错配和测试镜像缺 Node 的问题，并增加 YAML 结构/路径回归。普通 `offline.yml` 仍在 x64 宿主 Python 上执行，不会混用 ARM 二进制。

本机没有 Docker/QEMU，尚未执行这些容器构建/原生 runner 测试；当前通过的是本机离线回归、定义检查和 wheel 元数据核对。

## 主题与 Kindle Oasis 2

配置 → 主题提供明亮、暗色、墨水屏，沿用 revision 保存/应用/回滚。墨水屏黑白文字和边界，不靠颜色表达状态；关闭动画/阴影/过渡、隐藏灰阶装饰，SSE 改低频轮询，主要 DOM 仅在状态变化时更新。默认 60 秒，可设 15–300 秒。

Kindle 旧浏览器可能不支持主页面的现代 JavaScript，仅换颜色不够。专用 `/display` 是只读服务端渲染页：零脚本、系统衬线字体、黑字白底、普通表单登录和 meta 低频刷新；手机选择暗色不会把它变成暗底。

墨水屏布局可选自动/竖屏/横屏，设置位于配置 → 主题。也可直接访问 `/display?layout=landscape`；横屏将当前曲目与队列并排，不做 CSS 旋转，也不会强制改变 Kindle 的物理屏幕方向。自动模式随宽高选择排版，参数随刷新和登录保留。

状态页显示平台知道的当前歌名、歌手、来源、准备/播放状态和队列；不是只显示连接状态。原生蓝牙/DLNA 正在播放而没有曲目回传时显示“原生播放 / 曲目信息未回传”，不猜名称；“播放器报告播放”也不等于已确认听到声音。实际页面已以无脚本、1000px 横向视口和长测试曲名验证排版。

先在手机/电脑初始化管理员，再在 Kindle 打开 `https://<管理主机>/display` 登录；HTTPS/LAN 可达性按 [部署文档](11-R76s-部署与验收.md) 配置，不为旧设备取消证书校验或开放明文密钥配置。当前只验证 Chromium 600px 窄视口、无脚本页面和主题计算样式，不是 Oasis 2 真机认证；TLS/Cookie/实际刷新效果需要用户设备验收。原生蓝牙/DLNA 无曲目回传时不猜歌名。
